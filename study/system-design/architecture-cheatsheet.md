# Architecture talking-points cheat sheet

Originally built for a specific interview round, then generalized since the content isn't company-specific, to have concrete, opinionated answers ready for "how would you architect X" style questions — not vague "it depends" — while still explicitly flagging what's MVP-necessary vs. deferred.

**The core pattern to repeat per topic**: "we don't need X for the MVP, but I'd already build the app so X is a small addition later" — say this explicitly for each decision below, not just once. It signals product sense without over-engineering.

- **Scaling**: don't over-build for an MVP, but design the app **stateless** from day one (no local session/file state) so horizontal scaling later is additive, not a rewrite. For actually running things in parallel: start on a PaaS with autoscale (Fly.io / Render / Railway) rather than raw Kubernetes — less ops overhead to validate an idea. Move to ECS/EKS behind an ALB only once team size and traffic justify the ops cost.
- **Observability**: structured logging (JSON, request/trace IDs threaded through) from day one regardless of scale — this one isn't optional even at MVP stage. Tool choice: **Sentry** for errors + performance, minutes to set up, free tier — right fit for an MVP. **Datadog** is the most complete (logs+metrics+traces+APM) but pricier — graduate to it once there's budget. **Grafana stack** (Loki+Prometheus+Tempo) if optimizing for cost with more setup tolerance. **Graylog** only if there's already a team maintaining self-hosted log infra.
- **Database**: default to **Postgres** for almost everything — JSONB gives document-like flexibility without giving up relational integrity and transactions. Only reach for Mongo/NoSQL when data is genuinely unstructured and write-heavy at scale (event logs, freeform generated content) — don't run tw o databases without a clear need. At real scale: read replicas, PgBouncer connection pooling, later partitioning — well past MVP concerns, say so explicitly if raised.
- **Auth**: ask first whether the company already has something to integrate with (SSO, existing provider). If not, don't build from scratch: **Clerk** is a strong default for a React/Node stack — fast DX, ships with prebuilt UI. **Auth0** if enterprise SSO/SAML is a known future need. Existing **Supabase** stack → use its built-in auth to avoid adding a vendor.
- **File storage**: **S3** buckets, **CloudFront** as CDN for delivery, **presigned URLs** for direct client-to-S3 upload (skip routing large files through the API).
- **Networking / edge layer**: a **reverse proxy** sits in front of your actual server(s) and forwards client requests to them — the client only ever talks to the proxy, never directly to your app. **Cloudflare** is a common choice for this role: an independent provider (not part of AWS) that bundles termination behind one dashboard, and works regardless of where your origin is hosted. AWS's equivalent is assembled from separate services instead — Route53 (DNS) + CloudFront (CDN) + AWS WAF + ACM (certificates) + Shield (DDoS). Reach for Cloudflare (or an equivalent) when you want that bundle without wiring several vendors together — free tier makes it a reasonable default even at MVP stage, not just at scale.
- **AI integration**: don't call the LLM synchronously inside the request/response cycle for anything non-trivial — push to a queue/worker (SQS+Lambda or a simple job runner), client gets updates via polling or SSE/websocket. Validate model output against a strict schema (Zod on TS, Pydantic on Python) instead of trusting free-form text. Keep a thin abstraction layer over the model provider instead of hardcoding a single SDK everywhere — **this is a real lesson from** `local-llm-lab`: chat templates and tool-calling behavior differ enough across models/runtimes that hardcoding one is risky. Cite as real experience, not theory, if the conversation goes there.
- **Hosting**: first pass favors speed — Vercel (frontend), Render/Fly/ECS Fargate (API) — optimizing time-to-first-deploy over cost. As traffic becomes steady/predictable, reserved/spot EC2 or dedicated hardware gets cheaper than PaaS pay-as-you-go. The decision axis is **predictability of load**, not just raw scale — bursty traffic still favors PaaS elasticity even at higher unit cost. If you have real measured data here (e.g. your own GPU energy/cost benchmarking) — worth mentioning that cost tradeoff analysis for AI workloads specifically is something you've actually done, not just an opinion.
- **Frontend / design system**: ask if a brand/design system already exists — use it if so. If not, don't hand-roll components for an MVP: **shadcn/ui** (Radix + Tailwind) is a strong default — you own the component code (not a black-box dependency), which also plays well with AI tooling (Cursor/Claude Code can read and edit the actual component source, when such tools are allowed). Chakra UI is faster to start but less customizable. Always caveat: validate the visual direction with the client/founder before going deep — design-first conversation, not just picking a library.



## Process reminders (don't just answer the tech questions)

- Always give a rough time estimate, even approximate ("~2-3 days for a bare MVP of this scope") — signals product sense, not just technical depth.
- Explicitly narrate what's being **deliberately left out of v1 and why**, repeated per topic — the load-balancer framing above is the template.
- Ask clarifying questions before proposing a solution.
- Close the loop with "how would I validate this is working" — ties observability back to validating the product hypothesis, not just infra monitoring for its own sake.



## Execution-elegance idea

Beyond talking architecture, show delivery discipline: break the scoped work into a lightweight task backlog with dependencies/parallelism called out (e.g. "data model + auth can run in parallel, frontend can start against mocked data while the AI pipeline is built"), the way a Linear epic would be structured. If AI coding tools are allowed in a given round, scaffolding the repo live with Claude Code is a strong, authentic demo of AI-native fluency. If not allowed (as is the case for some take-home/live-coding rounds), the same task-breakdown discipline still works spoken/sketched, no tool needed.
